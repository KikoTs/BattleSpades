## Deployment

`scripts/steam_linux_sidecar.py` runs as the dedicated unprivileged account
`battlespades-steam`. It loads Valve's native x86-64 `steamclient.so` using the
versioned `SteamClient017` and `SteamGameServer012` interfaces. The interface
declarations are published in Valve's
[Steamworks 1.37 GameServer header](https://github.com/ValveSoftware/Proton/blob/proton_11.0/lsteamclient/steamworks_sdk_137/isteamgameserver.h)
and [SteamClient header](https://github.com/ValveSoftware/Proton/blob/proton_11.0/lsteamclient/steamworks_sdk_137/isteamclient.h).
No game-server login token or Steam account credentials were needed.

The runtime was downloaded directly from Valve's SteamCMD update CDN over
HTTPS. Its package size and SHA-256 were checked against the official
`steam_cmd_linux` manifest before extracting the three exact library paths.
The package SHA-256 was
`86e42113ed6391d73f727a40b536334b8ee5129890e11a0e42ed011feca2456c`.
The runtime is installed only on the VPS and is not committed to this repo.

The sidecar reads the existing game's A2S_INFO and A2S_PLAYER responses on
loopback every five seconds. It mirrors the live name, map, capacity,
population, bot count, names and scores. It converts the old gameplay-ID tag
to the retail public-category tag and prefixes the map with `TDM_`.
After three failed upstream probes it withdraws its advertisement and exits;
systemd retries after 30 seconds. Startup requires a successful upstream query.

Steam's `SetBotPlayerCount` does not set total occupancy. The helper mirrors
each actual upstream player through the unauthenticated-user API, then sets
the actual bot count separately. This is browser metadata, **not validation
of human Steam session tickets**. Player IDs/durations in the Steam query
are sidecar bookkeeping and can reset when it restarts. Gameplay validation
and policy remain with the existing BattleSpades server.

| VPS path | Purpose |
| --- | --- |
| `/opt/battlespades-steam/steam_linux_sidecar.py` | Isolated native Steam helper |
| `/opt/battlespades-steam/check_steam_registration.py` | Shared bounded A2S parser |
| `/opt/battlespades-steam/runtime/` | Operator-installed Valve libraries and provenance |
| `/var/lib/battlespades-steam/` | Private Steam runtime state |
| `/etc/systemd/system/battlespades-steam.service` | Automatic startup/restart, 512 MiB memory cap |
| `/etc/systemd/system/battlespades-retail-port.service` | Persistent retail game-port alias |
| `/etc/battlespades-steam/retail-port.nft` | Single owned nftables NAT table |

Both new services are enabled at boot. The Steam helper measured about
22 MiB of memory after login. The port service owns only the
`ip battlespades_retail` table and redirects packets addressed to
`204.168.157.43:32887` to the existing local UDP 27015 listener. Connection
tracking preserves reply addressing and the original client source address.
UFW still filters the translated game traffic using its existing 27015 rule.
One narrow UFW allowance was added for public UDP 32888. The existing firewall
tables, SSH access, relay service, CTF, Zombie and TDM configurations were not
changed. The game process was not restarted.

## Verification

- Valve's live `GetServersAtAddress` response lists app 224540, directory
  `aceofspades`, query address `204.168.157.43:32888`, and game port 32887.
- A2S queries from the Windows development PC reach both new public ports.
  The Steam response includes the full 64-bit game ID, correct category tag,
  live map and real 12/24 occupancy.
- An external ENet protocol-168 session through UDP 32887 completed the
  initial handshake, map synchronization, state transfer and spectator join.
  It received 748 live world updates over a 27.5-second test and disconnected
  cleanly. This was a protocol probe, not the graphical retail client.
- During that session both the upstream game and Steam query reported
  12 players / 11 bots, and `SteamPortCheck` appeared in the Steam player list.
  After disconnect, the bot population returned to 12.
- Map rotation was observed: the advertisement followed ArcticBase to Atlantis.
- Restarting the isolated Steam helper successfully re-registered it.
  The existing TDM PID remained unchanged.
- Focused local tests: 33 passed (Steam configuration, metadata conversion,
  population bookkeeping, full A2S extra fields and malformed packet handling).

Actual appearance and joining through the **unmodified retail graphical
server browser** still need an in-game check. Registration, public queries,
the recovered native category filter and the game-session path are verified
separately; they do not constitute a screenshot of the retail list.
Use Internet **All** or **User**, with Europe/all regions and empty/bot-only
servers visible. The existing name contains "Official" as AoS Revival
branding; it is not Valve's official-server whitelist flag.

## Operations and rollback

```sh
systemctl status battlespades-steam battlespades-retail-port
journalctl -u battlespades-steam -n 50 --no-pager
nft list table ip battlespades_retail
```

From another network:

```powershell
py scripts/check_steam_registration.py 204.168.157.43 --game-port 32887 --query-port 32888
```

To withdraw only this retail entry and port alias:

```sh
systemctl disable --now battlespades-steam.service
systemctl disable --now battlespades-retail-port.service
ufw delete allow in proto udp to 204.168.157.43 port 32888
```

The original TDM remains reachable on UDP 27015. The Steam service's stop
path logs off; directory caches can take time to expire. The port service's
stop path deletes only its own nftables table. Do not flush nftables or UFW.
Deleting installed files or the service account is unnecessary for rollback.

Only one game instance per public IP can occupy the retail browser's fixed
UDP 32887 destination. Advertising CTF and Zombie on the same IP with other
game ports would make the stock client join the wrong instance. Additional
public IPs or a client change are needed for separate joinable rows.
